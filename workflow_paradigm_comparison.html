执行范式对比：从「人肉搬运」到「Agent 自主闭环」

左：范式 A · 本地改码 + 人工上传 + 回贴报错（`PROMPT_STANDARD.md` v1.1 时期） ·  右：范式 B · SSH 直连 + Agent 自主训练/迭代/纠错（当前）
固定项不变：TRAE + DeepSeek-V4-Pro（禁 Auto）、temperature=0.7、seed=42、5 折分层 CV、官方协议评估

01两列对比表（核心页）

同一套研究目标、同一个模型、同一个 seed —— 唯一变量是"谁在执行、谁在搬运、谁在纠错"。

对比维度 范式 A · 人肉搬运（v1.1 时期） 范式 B · Agent 自主闭环（现在）
① 代码在哪改 AI 在本地 TRAE 生成代码，落在本地磁盘 Agent 直连服务器，直接读 / 写 / 改远端文件
② 代码怎么同步 人工手动 scp / 复制粘贴上传到服务器 无不存在"同步"这一步，Agent 直接操作远端
③ 命令谁执行 人工人在服务器终端手敲命令 Agent经 .ssh_keys/remote.py（paramiko 免密）自主执行
④ 报错回路 人工往返人复制报错 → 粘贴给 AI → AI 改 → 人再上传 → 再跑，每一轮都要人接力 闭环Agent 直接读 stderr / train.log → 自行定位 → 最小修复 → 自动重跑
⑤ 单轮迭代耗时 分钟 ~ 小时级，卡在人的往返与在线时间 秒 ~ 分钟级，无人工等待；可连续自主迭代
⑥ 长时训练管理 人工人守着终端，手动 nohup，断了要重连 Agentsetsid nohup 后台启动 + 主动轮询日志监控（断网不影响）
⑦ 人机干预计数 human_intervention_count 每次改码 / 上传都 +1（数值高） 人工干预趋近 0；新增 agent_ops_count 记录 Agent 自主动作数
⑧ 可复现留痕 人工靠人手工记录命令与日志，易漏记 命令 / 日志自动落盘：remote.py 输出、train.log、RESEARCH_LOG 三层记忆
⑨ 上下文连续性 人搬运时报错易被截断、上下文丢失，AI 只能看到人转述的片段 Agent 全程持有完整上下文，零信息损耗，能追溯到原始日志
⑩ 主要风险 人成瓶颈；粘贴不全；重复劳动；人误操作 Agent 跑偏 / 幻觉 / 误操作（GLaS 误锁 UNI、CNN 路线翻车）→ 必须配护栏
⑪ 本项目实证 PUMA：UNI 手写方案，人上传训练 → TTA Micro Dice 0.6762 DRIVE / GLaS：Agent 自主 5 折训练 + 官方口径评估 + 自主纠错 → CV Dice 0.7990 / 0.9276

02流程对比：线性人肉 vs 闭环自主

范式 A · 人肉搬运（人在回路中，是瓶颈）

每跑一次实验，人都要在"AI → 服务器 → AI"之间搬运两次。

① 本地 AI 写码→ ② 人上传→ ③ 服务器执行→ ④ 人复制报错→ ⑤ AI 改码↺

↺ 回到 ② —— 每轮迭代都需要人接力，人不在就停摆

范式 B · Agent 自主闭环（人只在关键节点审核）

Agent 自己完成"执行 → 读日志 → 诊断 → 修复 → 重跑"的闭环，人退出日常回路。

① Agent 写码→ ② SSH 直连执行→ ③ 读 train.log / stderr→ ④ 自诊断 + 最小修复↺

↺ 回到 ② —— 全自动闭环；人只在「定方向、审关键结果、确认破坏性操作」时介入

04一句话讲稿

"我们最初是人肉搬运：AI 在本地写码，人上传到服务器，跑完再把报错贴回来 —— 人卡在回路里，是瓶颈。现在我们让 Agent 直接 SSH 连服务器，自己执行、自己读日志、自己纠错、自己重跑，人退出日常回路，只在定方向和审关键结果时介入。所以这套 PROMPT_STANDARD.md 要从 v1.1 升级到 v2.0 —— 因为 v1.1 的元数据只记'人改了几次码'、工作流写成'写码给人上传'，这些字段和步骤在自主范式下全部失真，必须换成能记录 Agent 自主动作、并能给人机干预量做对照的新版本。"
